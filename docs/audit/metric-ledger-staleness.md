# The metric ledger was five rows behind its own sources

**Date:** 2026-10-31
**Surface:** `docs/METRIC_LEDGER.md` + `docs/METRIC_LEDGER.json`
**Change:** regenerated; new `--check` mode; wired into the gate chain (entry 24)
**No result number, status label, verdict or claim changed.**

## 1. Observed

`METRIC_LEDGER.md` opens with its own provenance: *"Generated by
`tools/build_metric_ledger.py` (133 rows)"*. Regenerating it produces **138**
rows:

| Row kind | On disk | Regenerated |
|---|---:|---:|
| CLAIM | 80 | 84 |
| INSIGHT | 18 | 19 |
| others | 35 | 35 |
| **total** | **133** | **138** |

Every row's `source_artifact_sha256` also pointed at an older `docs/CLAIMS.md`
(`baf1e11a…`; the file is `8f98bfc5…`). The "Build errors" section listed
CLM-070…CLM-084 as unparsed statuses; the current file lists CLM-085…CLM-088.

Nothing compared the generated files to a fresh render. `regen_audit_index.py`
has had `--check` since the audit index drifted the same way, and
`paper_evidence.py` has had one since the register drifted; the ledger — the
inventory that claims to be "the single machine-readable inventory of every
metric the project ships" — had neither.

## 2. Why shape-only comparison would not have caught it

Most of the drift changes no line count: a refreshed digest on an otherwise
identical row, or a status word on one row, leaves 133 lines in place. The
check therefore compares rendered content line by line and reports the first
difference with both sides, rather than comparing sizes or hashes of the whole
file (a whole-file hash gives the same answer with no location).

## 3. What changed

* `tools/build_metric_ledger.py --check` builds in memory, compares both
  rendered outputs to disk, and exits 1 naming the first differing line. It
  also fails when a file is missing, which is the fail-closed branch the
  `drift_33` gate lacked.
* `docs/METRIC_LEDGER.{md,json}` regenerated from the current sources.
* Gate chain entry 24, CI step, `AGENTS.md` §4.1 (24 entries; the ledger check
  is called out separately because it re-runs the five engineering gates and
  takes about a minute rather than seconds).
* Tests: `tests/test_tools/test_metric_ledger_check.py` (4 cases).

## 4. Observed, not changed

* Four claims (CLM-085…CLM-088) parse with status `UNKNOWN` and default to
  ACTIVE in the ledger, and two (CLM-018, CLM-022) carry the non-standard
  status `ACTIVE — INVERTED POST-cd70821 (see note)`. The ledger reports both
  as non-fatal build errors, which is what it should do. `docs/CLAIMS.md` is a
  frozen wording surface; correcting those rows is a claims edit, not a
  ledger edit, and this pass does not make one.
* The ledger's live pytest row (`--collect-only`, `5813 tests collected`) is
  lower than the outcome count in the same run (`5664 passed / 180 skipped`).
  A module-level `pytest.importorskip` contributes a skipped outcome and no
  collected item, so the two numbers are not expected to agree. Both are
  correct; they measure different things.
