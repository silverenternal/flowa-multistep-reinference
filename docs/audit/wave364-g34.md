## 3. Interpretation (why this closes G34)

The Wave 268 strict-clean rule is referenced 8+ times in `docs/drafts/paper-A-final.md` (in §3.5.1 / §7.6.2 / §7.7.1 / §7.8 / §7.cell-status-summary / §A.1.7 / §A.2.7 / §A.3.5) and many more times across the rest of the project (`docs/audit/`, `docs/drafts/paper-flat-flattened*.md`, AGENTS.md §3.7 "Stricter = cleaner" directive). Until now, the rule was implicit — every wave cited "Wave 268 strict-clean" as the authority for ADDITIVE-only edits, but the rule's verbatim text was never written down in any single canonical location. A reviewer landing on any of those references had to triangulate the rule's meaning from the surrounding context (the verbatim prose preserved + the "ADDITIVE" attribution pattern + the audit-trail references).

§3.9 closes this gap by:
1. **Surfacing the rule verbatim** — the rule text reads: "Wave 268 strict-clean rule: ADDITIVE blocks may add new content but must not modify, promote, or remove existing content; this rule prevents post-hoc number changes." This sentence is the canonical definition; any future citation refers to it.
2. **Naming the rule's three binding scopes** — (a) status labels in §7.2 / §11.1 (history-additive, no promotion of `UNDERPOWERED` / `DEFERRED` / `REGRESSES` / `NOT_SIGNIFICANT` to `SUPPORTED` by wording alone); (b) numerical claims (FID %, pLDDT Δ, scPerplexity Δ, Cohen's d_z, Bonferroni p, status counts are byte-stable across all later waves); (c) CLM-NNN rows in `docs/CLAIMS.md` (additive evidence rows without changing the canonical status field). These three scopes are the binding constraints every later wave must honour.
3. **Citing the audit doc once** — `docs/audit/wave268-strict-clean.md` is the canonical audit-doc handle. The §3.9 paragraph cites it once, providing the reviewer a one-click navigation to the rule's source wave (Wave 268 P4 final verification — README cleanups + audit doc, commit `9ecac78`) and its governance scope.
4. **Positioning the definition at the end of §3** — §3 is the framework's identity section (the "what the loop is" section), and the strict-clean rule is itself a framework-level convention that governs how all later waves interact with §3–§11. Placing the rule at the end of §3 (immediately after §3.8 "Why the framework's identity is the typed contract") makes the rule a natural extension of the framework-identity discussion: §3.1–§3.8 describe what the framework IS; §3.9 describes the governance convention that protects the framework's prose from post-hoc edits.

The §3.9 paragraph is intentionally explicit: *"Citations to 'Wave 268 strict-clean' or 'strict-clean rule' throughout the paper refer to this convention."* This sentence makes the citation → definition linkage unambiguous, so that no reviewer can mistake the rule for an unwritten convention or for an aside.
